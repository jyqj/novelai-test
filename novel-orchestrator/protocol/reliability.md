# 写作可靠性与创作自主性

本协议定义当前版本的写入、评审、历史视图和创作权限。它替代旧文档中“默认 pass”、全工作区清理、任意重用评审、知识只能在所有阶段使用的约定；原有文件命名和主循环仍见 formats / workflow。

## 1. 作品保护，不依赖 agent 自律

所有项目 CLI 修改通过单主机写锁和逐文件事务边界。每个实际修改的文件先记录前镜像与预期哈希，普通异常整体回滚；进程中断留下未完成事务，后续修改拒绝执行。

```bash
python3 "$NOVEL" recover                  # 只列出未完成事务
python3 "$NOVEL" recover --rollback       # 校验全部文件后，回退本次事务
python3 "$NOVEL" fsck
```

恢复若发现作者后续编辑，拒绝覆盖任何文件。先备份并人工协调冲突，再恢复；禁止全库 reset/clean。旧版仅有 done=false 的 journal 无前镜像，不能自动恢复，须人工查证。不要把旧 journal 改成 done=true 冒充恢复。

`tree add` / `entity new` / `thread new` 只创建不存在的目标。`write` 只能首写 planned 章；已有稿用 `revise`，版本递增，旧评审失效。published 章不能经任何正常写入入口覆盖，直接 `tree set-status ... published` 也被拒绝。发布仍是本地状态迁移，不是外部平台上传。

同一已消费任务的完全相同提交重试为无副作用 no-op；更换输入必须新任务。Git 提交只包含本命令触及路径；无身份、无 Git、存在作者已暂存内容时不接管作者索引，并明确提示。Git 是版本历史，不是事务恢复的唯一依赖。

## 2. 评审证明“检查了什么”，不证明“文学上优秀”

初次正文和 writeback 先提交为 drafted，再对这份确切产物生成待裁定清单：

```bash
python3 "$NOVEL" review checklist ch_0001 > /tmp/ch_0001.review.json
# 评审者阅读正文与简报，填写 summary 和每项 disposition/rationale；保留原 id/hash。
python3 "$NOVEL" review add ch_0001 --depth light --verdict pass --evidence /tmp/ch_0001.review.json
python3 "$NOVEL" gate approve ch_0001
python3 "$NOVEL" tree set-status ch_0001 approved
```

清单中的 pending 必须逐项裁定；pass/waived 必须有理由，waived 是有证据的审美例外，不是豁免机械硬错误。新增阻塞项也不能随 pass 混入。不得由脚本批量填写“通过”；tests/support.py 的合成票只用于工程测试。

回执绑定章内容、修订号、writeback、任务卡、简报、项目风格与判据。任何被绑定输入变化后重新生成清单并复评。轻评 pass 不能覆盖同版本深评 revise/escalate；同深度复评或新版本才可解决，旧票归档 reviews/history/。

发布前重新检查正文和回执；批准不是永久豁免。**目前机械回执范围是一章**。深评可以阅读一弧，但其单章票不自动替其他章节背书；报告应列受影响章号并分别开返修/复评任务。

## 3. 过去、计划与解释分开存

任务卡可选 `context_entities`、`memory_keywords`、`fact_refs`、`memory_refs`。实体关系、人物内在驱动不再按前十四行截断。简报以目标章之前为历史截止点；未来弧光明确标成计划，不能当已发生事实。

writeback 的可选 `narrative_memory` 保存重要后果、关系、承诺、意象、信念、情绪或场面：

```json
{"kind":"relationship","text":"救援之后乙把自己的依赖理解为羞辱，而不是感激。","entity_ids":["char_yi"],"thread_ids":[],"keywords":["救援","羞辱"],"evidence":"乙把递来的手推开了。"}
```

`evidence` 必须逐字出现在本章正文中；解释仍需评审，不能因引用存在就判真。每章通常记 0–3 条真正会影响后文的条目，不把整章再抄一遍。`memory_refs: ["ch_0001#0"]` 是明确依赖，必须召回；缺失、未来引用或必需信息超预算会拒绝编译，不静默丢弃。

`knowledge grant ... --ch ch_0010` 记录获知事件与授予时成员快照。离开组织不会遗忘，入伙不会自动获得旧秘密；需要新获知场面并再次 grant。`knowledge query --at ch_0009` 查看历史边界，读者揭示由 revealed_reader_ch 控制。

旧数据没有获知时间或实体历史快照时，系统会标注不确定或缺失，不捏造历史。新 grant 对旧记录的迁移只在明确章号记录快照，不回填成开书就知情。返修旧章后，下游因果、已知信息和叙事记忆仍须人工/模型复评；本版不是完整双时态数据库。

简报 manifest 记录依赖内容哈希、源集合、保留/裁剪项和输出哈希。补包应修任务依赖/源资产后重编译；禁止手改简报后再伪造 manifest。预算不足先删无关材料或拆场，不丢必需关系和事实；字符预算不是精确 tokenizer 上限。

## 4. 把硬事实与审美建议分开

硬约束包括事实/知识边界、作者明确禁区、授权范围、契约格式和本章约定字数。项目 style 中登记的文字黑名单仍由工具严格检查；作者认可例外时必须先修订项目 style，再复评，不能口头越过闸门。

节奏比例、句长、比喻次数、描写占比等方法论数值是诊断起点，不是跨作品通用定律。排比、缓慢场面、复杂独白可以成立；评审要指出具体效果与证据。连续同首句只报警，不自动判为坏文学。任务的情感与关系变化也可以承载章内进展，不强迫每章都靠更大危机推动。

写手可以把超出授权范围的新创意写进 issues，使用 `proposal:` 前缀：说明替代方案、为什么更好、影响实体/章节和代价；**提案不是 canon**，不得直接进入 continuity_delta。编排者验收/作者批准后修任务或设计，再写正文。小尺度的动作、细节与语言选择不需层层开庭。

作者可以显式推翻旧选择。记录 author_override、原决策、理由和下游影响；预算耗尽也不能把尚未解决的核心阻塞自动升级成“通过”。压缩范围或暂停该支线，保留失败尝试。无人值守不能替作者放宽红线。

## 5. 正反馈和验证

评审除指出失败模式，也保存成功片段与其作用：引用、为何有效、适用场景及边界。可放入 evidence.strengths（随回执保存），由编辑选择性沉淀到项目 style 范文锚；不直接把成功句式变成全书模板。

每弧至少一次冷读：不先看计划，只读正文，报告记住的人、在乎的关系、具体疑问、失去兴趣的位置；然后才和计划对照。LLM 模拟读者是候选反馈，不等同市场验证。实验方案见 evaluation.md。

## 6. 保证边界

此版本覆盖单主机 CLI 写入的进程崩溃/重试保护，不是跨主机分布式锁或完整掉电耐久数据库。直接手改仍由作者控制，published_hash 负责发现正文变化，不是文件权限沙箱。查询/rollup 仍有全量扫描；没有声称百万字性能或真实文学质量已经获证。
